Completed 23 November 2026 Blender 4.5 40 actions · 8 other wordings · 5 procedures 4 tasks 17 catalogued novice mistakes 12 closed-loop runs, both agents Gemini 3.8 Flash

Software-use simulation, first software Blender: a user's sentences become steps on the real window, one frame per tick

The digital counterpart of our device simulation. A user's sentence from a listed vocabulary becomes a short program of steps on the real Blender window running under a virtual display: the cursor travels, a menu pops open, an operator runs. Every 1.2-second tick the window is captured as one frame and the scene is read back as a graph, so sub-goals are re-checked every tick instead of latched. Four donut tasks from a public coaching dataset run end to end with stand-in agents (4 of 4 complete every sub-goal); one clip per action shows the vocabulary. Then the two agents go in: a simulated user that speaks and acts from a persona card and an assistant that watches the window and can only talk, with a hidden mistake forced on the user in every run. 8 of 12 runs finish with every sub-goal; the assistant never caught the forced mistake before it was committed (the window shows nothing until the wrong value is set), but it named it afterwards in 11 runs, and the user then recovered in 8 of those.

Motivation

Our device simulation runs a closed loop on a coffee machine: a simulated user acts, an assistant watches rendered frames and can only talk. Each new physical device there costs a 3D model, forty-odd hand-animated action families and a render farm. Software is the cheaper world to scale in: the application draws its own screen, its document is the state, and its operations are the action space. This experiment builds that world for Blender and wires it to the same interfaces, so the loop can be moved over without rewriting it.

The tasks and the mistakes come from a public dataset of human coaching sessions (seventy-two sessions in five applications, with screen recordings and labelled dialogue). Its four Blender tasks are the classic donut tutorial: model the donut and its icing, give them materials, make the donut fall, scatter sprinkles. Its coaches' diagnoses of what learners did wrong became the catalogue of mistakes that the loop below schedules.

The simulator and its contracts were built first, with a stand-in user replaying each task sentence by sentence and a silent stand-in assistant polled every second tick with the last eight frames. The two real agents then took those places (the loop, below).

Tasks, initial files and the mistake catalogue come from DigitalCoach (Chen et al., EMNLP 2026; released under CC BY 4.0): seventy-two expert–novice computer-use coaching sessions across Figma, Blender, Onshape, FL Studio and Excel, with screen recordings, input events, file snapshots every ten seconds and dialogue labelled by coaching method.

Pipeline

Figure 1 is the whole simulator; the others open on click and show one part each.
Figure 1. The whole simulator: a sentence in, a frame and a scene graph out

Read it top to bottom. A sentence from the user agent (in step 1 the fake user that replays a task) is parsed against the listed forms; anything else comes back as a refusal with the forms. A parsed sentence is bound to the open file (which object `the icing` is) and expanded into a short UI program: the cursor travels, a menu pops, an operator runs. One step runs per tick of 1.2 s.

Inside Blender a small server executes the steps on the real window, lets it redraw, and copies the virtual display's framebuffer into a PNG with the cursor drawn in. The same tick returns the scene graph: every object with its vertices, modifiers, materials and keyframes, plus the window's workspace, shading and mode. Sub-goals are conditions on that graph and are re-checked every tick.

Figure 2. From a sentence to UI steps: the parser, the binding, the plan

The sentence is matched against the families' templates in table order, then the aliases; a slot such as <modifier> accepts only the listed words, so the arguments come out typed. The object word is resolved on the current scene graph: a role from the program (the donut = Torus.001), an exact name (torus.002), a base name when it is unique, or the camera by type; an ambiguous or unknown word is refused with the names that exist.

The plan is a list of whole-tick steps. Every plan starts with a warp: the cursor travels to an anchor measured on the factory layout (the wrench tab, the Add Modifier button) or computed live (an object's projected position, an outliner row, a frame on the timeline). Menus really pop open; moving the cursor away closes them. When the object is not yet active, two steps come first: the cursor goes to its outliner row and clicks it, because the properties editor shows the active object's tabs.

Figure 3. One tick inside Blender: run the step, redraw, capture, read the state

The client sends `tick`. In the next timer callback the server runs the due step with the right editor as context (the 3D viewport, the properties editor, the node editor) and tags every area for redraw. A quarter of a second later, after the window has redrawn, it reads the virtual display's framebuffer file, draws the cursor arrow at the last warp, writes the PNG and serialises the scene graph. Blender's own screenshot operator is black under software OpenGL, which is why the framebuffer file is read instead.

A step that cannot run (a modifier on the camera, an extrude outside edit mode) raises with the reason; the rest of that action's steps are dropped and the action is reported failed with the reason, exactly like a refused sentence.

Figure 4. The state as a scene graph, and a sub-goal on it

Every tick the file is serialised into nodes with attributes: one node per object (type, vertex count, location, scale, smooth shading, the modifiers by type with their settings, the materials and the first base colour, the keyframes, the instances the geometry nodes produce), one per material, and a `blender` node for the window (workspace, shading, mode, frame, the active object). A sub-goal is a conjunction of conditions on these attributes; a node that does not exist yet, or a modifier that is absent, makes the condition false rather than an error.

Because the graph is re-read every tick, a sub-goal can go true and false again; the record keeps when it was first true and last true. The example is the materials task's second sub-goal; the last two graph rows are from the fall and sprinkles tasks.

Settings

A tick is 1.2 s of simulated time; a real tick takes about 0.4 s of wall-clock time, the first material preview about 6 s while shaders compile.
The window runs under a virtual display with software OpenGL on one slice of a GPU node; nothing is rendered with a path tracer.
Software
Blender 4.5 LTS, factory layout, one window of 1920 × 1080; the user's actions run inside it through its Python.
Observation
one PNG of the whole window per tick, read from the virtual display's framebuffer; the cursor arrow is drawn at the last position the user moved it to.
Action space
40 primitive sentence shapes with typed slots, 8 other wordings that map onto them, 5 procedures (named lists of primitives that the user never says). Any other sentence is refused with the list of forms.
Execution
a sentence becomes 1 to 6 whole-tick steps (the cursor travels, a menu pops, an operator or a property set runs); menus really open and close; a step that cannot run fails the action with its reason.
State
the scene graph read from Blender every tick (objects with vertices, modifiers, materials, keyframes, instances; the window's workspace, shading, mode, frame); sub-goals are conditions on it, re-checked every tick.
Tasks
the four Blender tasks of the dataset, as programs of sentences with sub-goals; each starts from the file the dataset's learners started from.
Agents
a stand-in user that replays the program and a stand-in assistant that says nothing; both use the reply contracts of the coffee loop.
Cost
a task of 20 sentences runs in about a minute on one GPU slice; a clip in a few seconds.

Tasks

Each task is a program: the dataset's task description as the goal, the file its learners started from, the sentences the stand-in user says in order, and the sub-goals checked on the scene graph. The video plays at 0.8 s per tick; the list under it says when each sub-goal first held.

A tick is 1.2 s of simulated time; the videos play at 0.8 s per tick. The stand-in user says the next sentence as soon as the previous one has finished; a refused sentence costs no tick.

A hidden schedule forces two mistakes per task on the user, who then carries on as if nothing were wrong until the assistant names the mistake and the user accepts; a mistake the assistant catches before the committing step is "prevented", otherwise it runs and the user has to recover with the assistant's help.

Interfaces and the record

The engine takes a sentence and answers at once: accepted with the number of ticks it will take, or refused with a reason and the accepted forms. Each tick it returns the frame, the graph and which steps finished or failed. It also reports the sub-goal progress and a one-line description of the state for a prompt.

The user agent returns, per turn, a line to say, a verdict on the assistant, a move and its plan edits; the assistant agent returns a line to say and an error flag. Both contracts are the coffee loop's, field for field; the stand-ins fill them trivially.

The record of a run holds the conversation, the moves, the injected mistakes, every action with the tick it was issued and finished and its feedback, the sub-goals with the ticks they first and last held, the outcome, and one scene graph per tick.
